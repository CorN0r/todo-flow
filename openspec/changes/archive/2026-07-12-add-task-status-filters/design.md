## Context

TodoFlow 的 `Task` 已有 `is_completed`、`is_suspended`、`is_abandoned` 和 `is_archived` 字段，桌面仓储、内存仓储与 Rust 查询层也支持这些布尔条件。当前差距主要在展示层：`TodayPage`、`DateFilterPage` 和 `MyDayPage` 各自复制了完成/超期判定，`TagPage` 没有状态筛选，移动端 `MobileTasksPage` 只有全部/未完成/已完成三种本地筛选，并且会预先排除已放弃任务。

桌面端同一任务集合还可切换列表、便签墙和一体式视图，并支持排序、拖拽与批量选择；移动端状态筛选会与搜索、标签和排序组合。因此该变化需要共享领域判定和一致的页面接入，而不是只扩展一个页面的按钮。

## Goals / Non-Goals

**Goals:**

- 为全部、进行中、已完成、挂起、已放弃和超期提供唯一、可测试的判定语义。
- 让桌面主要任务集合页和移动任务页使用一致的筛选结果与计数。
- 延续现有桌面标题栏与移动芯片的视觉语言，并在窄宽度下保持可用。
- 保证筛选与视图切换、搜索、标签、排序、详情选择和批量操作正确组合。
- 复用现有本地数据和仓储能力，不增加数据库或同步协议复杂度。

**Non-Goals:**

- 不改变任务状态字段、状态切换规则、数据库 schema 或同步协议。
- 不在本次变化中重做高级搜索页、看板、四象限、日历和小组件的专用筛选体验。
- 不增加多条件布尔筛选器、自定义保存视图或跨设备同步筛选偏好。
- 不将子任务提升为独立的根级筛选结果；子任务继续作为命中父任务的上下文展示。

## Decisions

### 1. 以共享分类器定义互斥主状态

新增共享模块（建议为 `src/lib/taskStatusFilter.ts`），导出 `TaskStatusFilter`、`classifyTaskStatus`、`matchesTaskStatusFilter` 和 `getTaskStatusCounts` 等纯函数。主状态采用以下优先级，确保异常组合不会同时落入多个互斥计数：

1. `abandoned`：`is_abandoned` 为真。
2. `completed`：未放弃且 `is_completed` 为真。
3. `suspended`：未放弃、未完成且 `is_suspended` 为真。
4. `active`：未放弃、未完成且未挂起。

`all` 匹配当前页面基础范围内所有未归档根任务；`overdue` 是派生视图，仅匹配 `active` 且截止时间早于本地当天的任务。选择优先级分类而不是直接组合布尔表达式，可以保证每个任务只有一个主状态，并统一目前页面间不一致的“未完成”语义。

### 2. 在前端基础集合上筛选并计算计数

桌面页面继续一次性读取当前路由对应的基础集合（日期范围、我的一天或标签），完成嵌套后只对根任务分类。移动端先应用归档、根任务、搜索和标签约束，再计算状态计数。统一处理管线为：

`基础数据 -> 页面/搜索/标签范围 -> 状态计数 -> 状态筛选 -> 排序 -> 视图渲染`

采用客户端筛选是因为当前本地任务集合已经被页面加载，状态切换需要即时响应，并且控件要同时显示各状态计数；若改为每个状态单独查询，会增加多次仓储调用和缓存组合。筛选与计数使用 `useMemo`，避免无关渲染重复计算。

### 3. 抽取响应式状态筛选控件

桌面端从 `PageTitle` 中抽取可复用的状态筛选控件。宽屏标题栏保留与现有圆角状态标签一致的紧凑分段入口，优先展示“全部、进行中、已完成”；挂起、已放弃和超期放入带 `Filter` 图标的菜单，菜单始终显示各项计数。选择次级状态后，触发按钮显示当前状态和计数并呈激活态。空间不足时收敛为单个过滤按钮，菜单包含全部六项，避免标题和操作区换行碰撞。

移动端保留现有 `MobileChip` 交互，在状态行中提供六个带计数的选项，并允许横向滚动或稳定换行；触控目标继续满足现有移动设计令牌。所有状态选项即使计数为零也可选择，以避免按钮随数据变化跳动。

### 4. 筛选状态按使用场景保存

桌面端在 `uiStore` 保存会话级 `taskStatusFilter`，默认值为 `all`，并在今天、日期范围、我的一天和标签页面间保持选择；应用重新加载后恢复为 `all`，避免用户再次打开应用时落入难以察觉的空筛选。移动任务页保留其当前产品默认值，但将 `open` 明确替换为 `active`，即默认隐藏已完成、挂起和已放弃任务；重新进入移动任务页时恢复该默认值。

### 5. 保持视图和操作作用域一致

页面只把筛选后的根任务传给 `TaskList`、`StickyWall` 和 `UnifiedLayout`，因此三种桌面视图必须显示相同集合。筛选变化后：

- `selectableIds` 更新为当前可见根任务，已有批量选择与新可见集合取交集。
- 若一体式视图当前详情任务不再可见，则清除 `selectedTaskId`。
- “全选”和批量操作只作用于当前可见任务。
- 手动拖拽筛选子集时，必须把可见顺序稳定合并回未筛选基础顺序，再持久化完整根任务顺序；隐藏任务保持原有相对顺序，不能仅用筛选结果重写从零开始的 `sort_order`。

### 6. 区分数据为空与筛选无结果

基础集合为空时继续使用各页面原有空状态。基础集合非空但状态筛选结果为空时，显示与当前状态对应的“没有挂起任务”等反馈，并提供“显示全部”操作。状态变更只改变展示，不自动改写任务字段，也不会因为计数为零而偷偷切回全部。

### 7. 文案与可访问性进入现有国际化层

新增中英文状态名称、计数、筛选无结果和“显示全部”文案。桌面菜单使用可聚焦的按钮和明确的 `aria-pressed`/选中状态，图标按钮提供名称；移动芯片维持可访问名称和现有最小触控尺寸。

## Risks / Trade-offs

- [历史数据可能同时具有多个状态标记] -> 使用固定分类优先级并为组合状态添加单元测试，保证计数互斥且结果可预测。
- [六个选项挤压桌面标题栏或移动首屏] -> 桌面使用主选项加菜单并在窄宽度下完全收敛，移动沿用可滚动/换行芯片行。
- [多个页面继续复制筛选表达式后再次漂移] -> 页面只能调用共享纯函数，并用跨页面测试锁定同一组夹具结果。
- [筛选后拖拽会破坏隐藏任务顺序] -> 使用完整基础顺序做稳定合并，并覆盖隐藏项相对顺序的回归测试。
- [客户端筛选在超大列表上增加计算] -> 仅处理当前页面已加载的根任务，使用 memoization；现阶段无需引入额外查询和缓存复杂度。

## Migration Plan

1. 先加入共享分类器、类型和单元测试，不改变现有页面行为。
2. 加入响应式桌面控件和国际化文案，再逐页替换重复筛选逻辑。
3. 接入移动任务页并补齐组合筛选测试。
4. 验证三种桌面视图、选择范围、空状态和筛选子集拖拽排序。
5. 本变化不迁移持久化数据；回滚时可移除新控件和共享状态，任务数据不受影响。

## Open Questions

当前没有阻塞实施的问题。高级搜索和专用视图是否复用该控件可在后续变化中单独评估。
