## 1. 目标与确认状态

把“库”升级成“工作区”：一个工作区是一个数据库文件加它的附件目录，同一时间只激活一个。用户和 Agent 可以把不同用途的数据分开、随时查看任一备份；除明确确认的删除外，没有操作会破坏现有内容。

| 已确认的方向 | 本稿如何落实 |
| --- | --- |
| 切换时重启应用，不做无感热切换 | 切换入口、重启等待、窗口位置和番茄钟计时保持，见 `workspace-switching` |
| 第一版只对当前工作区提醒 | 未激活的工作区不提醒，激活时立即检查；切换器中写明这条规则 |
| 偏好设置跟工作区走 | 外观和番茄钟记录属于应用；新建空白工作区时复制库内偏好 |
| 用“添加为新工作区”代替整库覆盖 | 不做覆盖；回到某个时间点时把备份添加成工作区 |
| 合并导入保留，并升级为先预览再勾选 | 默认只找回当前库中没有的任务，整次原子完成，见 `backup-recovery` |

四项选择均已审核确认，见第 5 节。

## 2. 三个典型使用场景

### 场景 A：Agent 写进了另一个库

用户曾经让 MCP 用 `--db-path` 写入别的文件。在“管理工作区”里把它从文件添加进来，应用重启后直接看到里面的任务。之后不再给 MCP 指定路径（跟随当前激活的工作区），或者用 `--profile` 固定写到某个工作区。

### 场景 B：误删了几个任务

用户在“设置 → 数据 → 从备份找回”里选一份备份。预览默认勾选当前库中没有的任务，执行后它们回到任务列表，其余任务、设置和模型配置不变。

### 场景 C：想回到某个时间点

用户把那一天的备份添加为新工作区并切过去，旧状态原样可用，当前状态原地不动。确认没有问题后，再删掉不要的那个工作区。

## 3. 交付范围

| 范围 | 第一版内容 |
| --- | --- |
| 工作区管理 | 清单与唯一激活、升级后原地登记、新建空白、从文件添加、重命名、删除、管理界面 |
| 切换 | 侧边栏切换器；重启等待、主窗口位置恢复、番茄钟计时保持；激活项不可用时回退 |
| 从备份找回 | 预览与勾选、默认只找回缺失任务、父子任务与依赖内容、单事务、可选的日／周回顾恢复（R4） |
| MCP／CLI | `--profile <名称>`；不指定时跟随当前激活的工作区 |
| 文件校验 | 添加与找回共用；不通过则拒绝，现有数据零改动 |

第一版不做：无感热切换、整库覆盖、所有工作区都提醒、任务跨工作区移动或复制、带附件的工作区包、把应用级设置从库里拆出。

## 4. 验收场景

1. 升级后首次启动，数据与升级前完全一致，清单里只有一个“默认工作区”。
2. 新建空白工作区后所有页面为空，语言与快捷键同原工作区；切回后原数据完整。
3. 从文件添加后，原文件字节不变，新工作区内容与文件一致；文件正被 MCP 进程使用时也如此。
4. 连续切换多次（包括番茄钟计时中、便签打开时），应用每次都能正常启动并打开选定的工作区，主窗口位置不变。
5. 番茄钟计时进行中切换，切换后计时继续，关联任务的标题保留。
6. 从备份找回：默认只新增当前库中没有的任务，已存在的不被改动；手动勾选的被备份版本覆盖；习惯等其他数据不变；“由 Agent 创建”标记保留；在本机删除的任务找回后附件可用。
7. 用比当前应用新的、损坏的或非 TodoFlow 的文件做添加或找回，都被拒绝，现有数据零改动。
8. 删除最后一个工作区被拒绝；删除后磁盘无残留目录，凭据里只剩其他工作区仍在用的密钥。
9. MCP 不带 `--profile` 时，界面切换后 Agent 新建的任务出现在当前激活的工作区；带 `--profile` 时始终写入指定的工作区。
10. 切换后立即检查新工作区的到期提醒，旧工作区的待处理提醒不再出现。

## 5. 审核选择（已确认）

| 编号 | 审核事项 | 结论 | 说明 |
| --- | --- | --- | --- |
| R1 | 切换方式 | 切换时重启应用 | 热切换的成本和长期约束不值每次省下的一两秒 |
| R2 | 提醒范围 | 第一版只对当前工作区提醒 | 未激活的工作区不提醒；激活时立即检查，含未激活期间到期的 |
| R3 | 偏好设置归属 | 跟工作区走 | 新建空白工作区时复制库内偏好；外观和番茄钟记录属于应用 |
| R4 | “从备份找回”是否保留“同时恢复日／周回顾”选项 | 保留，默认不勾选；进展记录改为跟着所选任务走 | 现有规格要求具备显式恢复能力（`task-progress-records`、`task-period-reviews`）。若去掉，需要同时修改这两份规格，而且误删的回顾文稿只能通过“添加为新工作区”后手工复制找回 |

### 实施中对方案的补充

- **跟随激活项的 MCP 服务每秒检查一次目标**，不只是等到下一次工具调用。否则用户刚切换完工作区、Agent 还没发起调用时，删除刚离开的工作区会提示“正在被其他程序使用”。
- **启动时完成“待删除”最多重试 5 次（间隔 600 毫秒）**，等常驻的 MCP 服务放开文件；仍不行才保留条目并提示。
- **找回任务时，随任务删除而被清空正文的进展记录按备份恢复**。原来的写法是“同 ID 就跳过”，那样找回的任务会是空的，历史回不来。本机上仍有效的记录照旧不动。

另外移除了旧的整库导入代码（`import_database` 命令和 `restore_progress_data` 及其配套函数），它们已经没有调用方。

### 真机验收

**环境**：Windows，玻璃主题。待验收的是独立构建的可执行文件（`cargo build --bins`，内嵌最新前端，不依赖开发服务器），运行在真实数据目录上。

**数据保护**：验收前用 SQLite 备份接口给真实数据库留了一致快照，并记下各表的内容指纹。每轮验收结束后比对。最后一轮发现 `settings` 里番茄钟窗口的位置偏好（`pomodoro_x` / `pomodoro_y`）被改写了：番茄钟在默认工作区里运行时，番茄钟窗口按原有行为把当时的实际位置存了回去。测试程序关闭后已按快照还原这两个值，最终比对结果是与验收前逐表一致（176 个任务原样）。测试用的工作区都通过界面上的“删除工作区”清掉了。

**还有一处没清**：浏览器本地存储里的番茄钟历史多了一条验收记录（“验收-番茄钟任务”，25 分钟）。它属于应用而不是某个工作区，会出现在默认工作区的数据面板里；界面里没有清除它的入口，清掉它要经调试接口写本地存储，留给用户决定。

“拆解生成中切换”那一项在测试工作区里配过一个假的模型服务，它的假密钥按应用的常规方式存进了系统凭据管理器。收尾时先在设置里点了“删除连接”让应用自己清掉，再删除工作区。系统自带的工具看不到这类记录，所以没能直接确认它已经清除；删除工作区时清理独占密钥的逻辑有单元测试覆盖。

#### 经界面操作的项

已经通过的：

- **新建工作区**：在管理界面里新建，应用 4.3 秒后重启，进入一个空的新工作区，窗口位置不变。
- **连续切换 10 次**：在两个工作区之间来回切，10 次全部成功。从点击到新窗口出现 3.3–7.0 秒，进入数据多的工作区更慢；每次窗口位置都不变，没有出现残留进程或卡死。
- **外部写入后界面自动刷新**：MCP 往当前工作区写入 4 个任务，界面 3 秒内自动显示。
- **提醒**：提醒在工作区 A 弹出后切到 B，B 里不显示它；切回 A 时立刻重新弹出。
- **管理界面在玻璃主题下的观感**：背景变暗模糊，对话框清晰可读。
- **任务数（修复后复验）**：管理界面显示“124 个任务”，与“全部任务”页面一致。
- **番茄钟计时跨切换**（两个问题修复后复验）：重启后恢复进行中的番茄钟；运行中来回切换两次，计时继续、会话起点不变、剩余时间与实际流逝吻合（没有被重复扣减），任务详情里仍显示“停止专注”；停止后本地存储里的会话记录立刻清掉，之后不再被写回，番茄钟窗口关闭。
- **桌面便签**：把一个任务固定到桌面后切到另一个工作区，便签不再出现；切回来时按记录重新出现。
- **经界面删除工作区**：删除非当前工作区时，清单条目和目录都被移除，应用不重启，当前工作区不变；删除当前工作区时，确认框多一行“会切换到另一个工作区并重启应用”，确认后重启并进入默认工作区，条目、目录和便签一并清掉。两种各做了两遍。

- **带系统文件对话框的“从备份找回”**：在设置里点“从备份找回…”→“选择备份文件…”，在系统的文件选择框里填入一份备份的路径。预览显示“备份里有 3 个任务，其中 1 个当前库中没有”，默认只勾选缺的那个，另外两个标着“已存在”；点“找回”后提示“已找回 1 个任务，替换 0 个”，那个任务以原来的 ID 回来，没勾的两个没动，备份文件的哈希前后一致。对话框在玻璃主题下清晰可读。
- **带系统文件对话框的“从文件添加”**：在管理界面点“从文件添加…”，选同一份备份，名称自动填成文件名，勾着“完成后切换过去”；点“添加”后应用重启进入新工作区，里面有备份里的 3 个任务。新工作区有自己的数据库和附件目录，备份文件的哈希没有变。
- **保存进行中切换**：`for-add` 是从 `acceptance-seed` 的备份添加出来的，两个工作区里任务的 ID 完全相同，正好能看出会不会串。在一边改任务标题、关掉详情、马上切到另一边，两个方向各做一遍：修改只落在原来那个工作区，另一边同 ID 的任务没被碰；切回来后修改还在。限度：从修改到点下切换最快也要 2 秒多，保存在关详情时就完成了，没法让保存恰好在重启那一刻还在进行。
- **拆解生成中切换**：测试工作区里配了一个只监听本机的假模型服务（三项验证都能通过；带有特定标题的请求一直不回应）。对那个任务点“AI 拆解”→“生成”，面板显示“生成中 · 已等待 N 秒”；等 54 秒后关掉详情、切到另一个工作区：那边没有任何生成状态和结果；切回来后任务没被改动（没有子任务，修改时间还是创建时间），详情里也没有残留的“生成中”，被挂住的连接在旧进程退出时就断了。全程没有调用真实的模型服务。
- **发布构建下的切换**（`cargo build --release --bins` 出来的可执行文件）：两次切换都成功——测试工作区到另一个测试工作区，再到数据最多的默认工作区。每次只有一个进程，窗口位置不变；点下之后旧窗口 0.5 秒消失，2.3 秒后新工作区显示出来。

- **`tauri dev` 下的切换**（第 9 条修复后复验）：`npx tauri dev` 启动后是“tauri 命令行 → cargo → 锚（约 10 MB，不运行应用）→ 应用”的结构。在两个测试工作区之间来回切了两次：每次应用都换成新进程并打开所选工作区，页面仍从开发服务器加载，命令、cargo、开发服务器全程都在，应用进程始终正好两个。结束当前应用，锚跟着退出、`npx tauri dev` 结束、开发服务器停掉；只结束锚，应用自己退出；改一个 Rust 文件触发自动重建，旧的两个进程被收掉，重新变回“一个锚 + 一个应用”。三种情况都没有残留进程。

#### 真机发现并修复的问题

1. **切换菜单被侧边栏的导航项盖住，点击落到了导航上。** 原因是我把菜单写成了侧边栏内部的绝对定位，违反了项目的 Portal 约定（玻璃主题下侧边栏是独立的层叠上下文）。已改为 Portal 加固定定位，层级按约定（菜单 200、对话框 300），并加了一条守护测试。
2. **玻璃主题下浮层是半透明的，后面的文字透上来。** 这个主题会把 `bg-white` 改写成很淡的半透明。菜单改用接近不透明的深色面板，对话框沿用搜索下拉的毛玻璃面板。
3. **启动提示带着英文的错误前缀**（“Validation error: 工作区…”）。新增 `AppError::user_message()`，直接展示给用户的说明不再带前缀。
4. **菜单的宽度样式类无效**（`calc` 里不能有空格），宽度实际没有生效。改为按按钮的实际宽度定位。
5. **番茄钟重启后不恢复。** 我把恢复出来的状态展开在初始状态对象的前面，但原有代码在后面还有一行 `sessionStartTime: null`，把恢复出来的会话起点覆盖成了空。后果是计时在走但窗口不显示，落盘逻辑还把存档删掉了。原来的测试只断言了“在运行”和剩余时间，没有断言会话起点，所以没抓到。已去掉那一行，并把测试补强（确认过：补强后的测试在有错误的代码上会失败）。
6. **管理界面的任务数和“全部任务”页面对不上**（显示 176，页面是 124）。管理界面把子任务也算进去了。改为只算顶层任务，和页面一致。
7. **点了“停止专注”之后，番茄钟的会话记录每秒被写回一次**（还是运行状态）。悬浮窗、番茄钟窗口、提醒和便签加载的是同一份前端代码，每个窗口里都有一份番茄钟状态；重启时每个窗口各自恢复会话、各自计时、各自写记录，主窗口里停止了，别的窗口还会把记录写回去。改为只有主窗口负责会话（恢复、计时、落盘），并补了针对四种次要窗口地址的测试（确认过：去掉这个限制，这 4 条会失败）。
8. **（原有问题，与工作区无关）关掉任务详情后马上点开另一个任务，后者的标题变成了前者的。** 详情面板里的 `TaskDetail` 没有 `key`，而面板不关也能换任务：关闭动画还没结束就点了另一条，或者面板开着时在搜索结果里选一个。这时同一个实例里的编辑状态被当成“未保存的修改”合并到新任务上并自动保存；上一个任务没来得及保存的修改也会写到新任务上。用真实的 `TaskDetail` 写了组件测试，确认在原有代码上稳定失败（不是时序问题）；改为按任务重建后通过，真实程序上连续 6 轮“关闭后立刻打开另一个任务”标题都没有变化。
9. **`tauri dev` 下切换工作区会打断开发会话（已修复）。** 切换本身是成功的：应用自己拉起新实例并退出，新实例打开了所选的工作区（点下到显示约 3.4 秒）。但 `npx tauri dev` 把旧进程的退出当成应用关闭，命令随即结束并停掉开发服务器（CLI 2.11.2）。于是新实例虽然还显示着界面，却已经不在开发工具的管理下；再切换一次，新实例启动时开发服务器已经不在，窗口里是“无法访问此页面（ERR_CONNECTION_REFUSED）”。留下的应用进程还会挡住下一次 `npx tauri dev`（单实例），要手动结束它。安装版不受影响（独立构建和发布构建都验证过）。根因是 Tauri 的 `request_restart()` 是“拉起新实例后以 0 退出”。修法见 `design.md` 的 D2：开发构建里被 `tauri dev` 直接启动的进程充当“锚”，应用实例切换时把后继者的进程号交给锚再退出，锚接着等。新增 `workspace/dev_handover.rs`，5 条单元测试用真实进程验证了等待、接棒和退出码；`tauri dev` 下的复验见上。只在开发构建里生效，独立构建和发布构建走的还是原来的重启。

### 没有验证的部分

- **`tauri dev` 下的进程交接只做了 Windows**，也只在小工作区之间验证了切换；macOS、Linux 的开发构建下切换仍会打断开发会话。
- **发布构建**下只测了四次切换（三次是加入 `tauri dev` 交接改动之前做的，其中一次进入数据最多的默认工作区；改动之后重新编译又做了一次切换，外加删除当前工作区引起的一次重启），没有像独立构建那样连续切 10 次。改动之后独立构建也复验了一次切换：仍是单进程、内嵌前端，和改动前一致。
- **发布构建**下只测了两次切换（进入数据最多的默认工作区的那一次也在内），没有像独立构建那样连续切 10 次。
- **移动端的条件编译分支没有经过编译验证。** 这台机器的 `NDK_HOME` 指向的目录不存在，Android 目标编不过。已逐行核对：移动端仍然打开应用数据目录下的 `todo.db`，`AppState` 新增的字段和新增的命令都不依赖桌面专有的代码。
- 界面验收用的点击工具默认同时走鼠标和可访问性两条路，可能做出真人做不出的操作组合（验收中就把主窗口的关闭按钮和详情面板的关闭键搞混过两次）。涉及“用户会不会遇到”的判断，以组件测试和纯鼠标点击的复验为准。任务多的工作区（默认工作区 124 个任务）里，主窗口的可访问性树会被截断，够不到侧边栏的切换按钮，只能用鼠标点击。

## 8. 后续优化建议

记下验收和讨论中提出来、这次没有做的优化，需要的时候再立项。

### 不重启的切换（运行中更换工作区，即“热加载”）

2026-11-25 讨论后决定暂不做：主要是为了切换体验，不急；先把 `tauri dev` 下的开发会话问题用进程交接解决。

- **现状**：切换 = 更新清单 + 重启应用。独立构建 3.3–7.0 秒、发布构建约 2.3 秒后新工作区显示出来；番茄钟会话和窗口位置靠应用级的持久化跨过重启。
- **做成之后**：切换几乎即时；不再需要重启，`tauri dev` 的进程交接、重启标记与单实例交接、番茄钟会话落盘、窗口位置恢复都可以删掉。
- **要动的部分**（按加入 `dev_handover` 之前的代码统计）：

| 部分 | 要改成什么 | 现状规模 |
| --- | --- | --- |
| 数据库连接和附件目录 | 运行中可替换。Tauri 2.11 没有替换托管状态的接口，连接一旦可替换，取连接的返回类型要跟着改 | 105 处 `state.db()` 分布在 14 个文件，另有 11 处直接加锁 |
| 两个后台线程 | 能停、能重启 | 提醒轮询和外部写入检测都是 `loop { …; sleep }`，没有停止机制；后者还盯着固定的数据库文件路径 |
| 便签窗口 | 全部关掉再按新工作区重建 | 每个便签窗口的回调各自持有一份数据库连接 |
| 从工作区设置初始化的东西 | 重新读一遍 | 全局快捷键（`shortcuts.rs` 467 行）、悬浮窗的位置和开关、番茄钟窗口位置、语言 |
| 启动流程 | 拆成可复用的“激活工作区”函数 | 现在都写在 `lib.rs` 的启动回调里 |
| 切换命令 | 加一道闸门，失败能退回 | 切换瞬间不能有在途的保存、AI 请求或“从备份找回”事务；新库打不开时要回到原工作区 |
| 前端 | 整体重置 | 11 类查询缓存清空；9 个 store 里与工作区绑定的要重置；还没落盘的编辑和进展草稿要先保存 |
| 其他窗口 | 各自收到通知并重置 | 悬浮窗、便签、提醒弹窗加载的是同一份前端代码 |

- **代价**：人工约 7–10 个工作日；验收要基本重做一遍，因为切换的方式变了。
- **多出来的风险**：切换瞬间的状态错位（写进旧库、旧线程晚到一个事件、窗口有残留），现在的重启方案里这类问题天然不存在；旧工作区的连接必须全部放掉，它所在的文件才能删。
- **建议的做法**：作为独立变更立项；先后端（可替换的连接、可重启的后台线程），再前端重置，最后真机验收。
